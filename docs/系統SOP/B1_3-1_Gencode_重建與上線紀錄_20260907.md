## 2. 本輪目標

本輪不重新建立 Skill，也不重新做題目分類。既有 `textbook_examples.skill_id` 與 classification 視為既定結果。

實際目標只有：

1. 每一筆 `textbook_example` 對應一個獨立 generator/component。
2. 可正常生成、答案正確、作答契約可用的 component 標為 `VERIFIED`。
3. 缺圖、缺表、題幹不完整、選項不完整的題目可直接 `SKIP`，不強求 100% 上線。
4. 同一個 `skill_id` 底下的 `VERIFIED` generators 由 Phase 3 包裝成同一個 skill wrapper。
5. Partial Publish 後進行 runtime smoke test。

核心原則：

> 一題一 generator；可用就 verified；壞題 skip；同 skill 的 verified generators package；再 publish。

## 5. Exact Readiness 修正

### 5.1 adapter_route 假陰性

原問題：Recovery / Exact Readiness 使用「adapter source 是否包含 operation 名稱」判定 adapter route，導致 generic adapter 被誤判為不存在。

實際 production 使用：

`core/gencode/domain_matrix_adapter.py`

`convert_domain_matrix_to_question_payload(...)`

修正後改以「正式 adapter callable 能否實際轉換 domain output」判定。

結果：

- `polynomial_long_division`：PASS
- `polynomial_add_sub`：PASS
- `polynomial_multiply`：PASS
- 其餘 3-1 polynomial operations：PASS

相關測試：`tests/gencode/test_adapter_route_readiness.py`。

### 5.2 selected_operation 空字串

原問題：confirmed binding 路徑只取得 skill routing，沒有把已分類 `problem_type_id` 帶入 operation selection，因此 `selected_operation=""`。

修正原則：

- required operation 以既有 classification／rule pack 為 authority。
- 只允許 exact registry / whitelist match。
- 不 fuzzy、不 fallback、不跨 domain。

修正後 3-1 正式分類 operations 的：

`selected_operation == required_operation`

全部 PASS。

相關測試：`tests/gencode/test_selected_operation_exact_resolution.py`。

## 8. 簡化 SOP / 後續章節 Runbook

之後做 3-2、3-3 或其他章節，沿用以下核心流程：

```
一筆 textbook_example
→ 一個 component / generator
→ generate + checker 基本驗證
→ VERIFIED 或 SKIP/FAILED

同一 skill_id：
→ 收集 VERIFIED generators
→ Phase 3 package
→ wrapper
→ publish
```

允許 Partial Publish。

### Step 1：確認 scope

- 取得該 section 所有 `textbook_examples`。
- 使用既有 skill / classification。
- 不重新分類。

### Step 2：一題一 generator

每題：

`textbook_example -> src_<id> -> generate.py / metadata.py / get_hint.py`

### Step 3：最小可用驗證

每題至少確認：

- `generate()` 可執行。
- fixed seed 可重現。
- question 完整。
- answer 與題目一致。
- answer topology / contract 可用。
- checker 正解通過、明顯錯解拒絕。
- 若教材為選擇題：維持 `single_choice`，四選項完整，shuffle 後正解 mapping 正確。

### Step 4：壞題直接隔離

若：

- 缺圖
- 缺表
- 題幹截斷
- choices 不完整
- source 無法安全還原

直接 `SKIPPED_SOURCE_INCOMPLETE`。

不要硬救，不阻擋其他題。

### Step 5：依 skill_id package

收集同一 skill 下的 `VERIFIED` components：

`verified components -> Phase 3 -> skill wrapper`

每筆 generator spec 仍是一題一 component。

### Step 6：Partial Publish

只 publish verified components。

不要求 100% 題目上線。

### Step 7：Runtime smoke

每個有變動的 skill 至少 smoke 20 次：

- 題目正常
- UI 正常
- checker 正常
- 無 500
- 無殘缺題

### 核心原則

- 不追求每題都上線。
- 缺圖／缺表／source 不完整可直接 skip。
- 單題失敗不阻擋同 skill 其他 generator。
- 不為單一 example 建 Domain 特例。
- source 有可靠教材證據時，先修 DB，再重新 Gencode。
- 同一 skill 的 verified generators 最後才 package 在一起。

這段將作為後續 B1 3-2 / 3-3 實作 Runbook 的基礎。

---

## 9. 什麼情況才停下來修架構

後續批次 Gencode 不再因每一個小問題停下來做大規模架構調查。

只有真正 blocker 才停：

- `DOMAIN_FUNCTION_MISSING`
- adapter 實際執行失敗
- selected operation 無法 exact resolve
- checker 完全不可用
- source 不完整
- Phase 3 package 無法建立 wrapper

其餘以「單題失敗隔離、其他題繼續」為原則。

---

## 10. 本次重要決策

1. 不追求所有教材題 100% 上線。
2. 題目品質高於 published 數量。
3. Source 不完整時不猜教材內容。
4. 一題一 generator。
5. 同 skill verified generators 才在 Phase 3 合併成 wrapper。
6. Partial Publish 是正常流程，不是失敗狀態。
7. source 有可靠教材證據時，先修 DB，再重新 Gencode。
8. 後續章節沿用本文件的簡化 Runbook，加速批次處理。
